# Codex 空会话发现

## 问题

Codex TUI 已打开且尚未发送首条消息时，当前版本不会及时触发 Tally 的 `SessionStart` hook。隔离目录中的 `codex --no-daemon --no-alt-screen` 实测：空窗口可见期间没有 hook 心跳及会话记录；退出后才出现结束记录。Tally 仅靠 hook 构建会话列表，因此空会话既不显示在 AI 页，也不触发入职工牌。

本机 Codex 状态库可包含未发送消息的真实会话 ID；在 `--no-daemon` 探针中，Codex 进程持有带该 ID 的 writer lock。共享后台模式中 hook 由后台进程运行，同目录多终端之间不能只按目录推断会话归属。当前尚未证实共享后台模式下终端 PID 与真实会话 ID 的可靠映射。

隔离 `CODEX_HOME` 的 Codex 0.166.0 探针同时打开两个同目录默认模式 TUI：两个 TUI 各有不同的 tty，两个会话的 writer lock 均由同一个后台进程持有；TUI 本身没有持有这些锁。空会话处于内存中时，隔离状态库的 `threads` 为零，不能靠查询数据库补齐。单独的 `--no-daemon` TUI 则由自身进程持有对应 writer lock。上述证据不足以建立默认模式的 ID 与 tty 映射，不能按时间或目录猜测。

## 目标与约束

- 空开的 Codex TUI 出现在 AI 页并触发一次入职工牌；发送首条消息后切换到真实会话状态，不重复发牌。
- 同目录多个 TUI、已有会话恢复、快速退出和 PID 重用不得合并成错误会话或跳错终端。
- 不修改 Codex 配置、数据库、凭据或终端启动命令；不向远端发送数据，不向用户的真实会话目录注入测试数据。
- 首次启动 Tally 和恢复开关的基线不补发旧工牌；减少动态效果和现有设置保持有效。

## 方案比较

1. **仅沿用 hook**：保持现有实现，无法覆盖空会话，不满足目标。
2. **以终端进程创建临时会话**：可较快显示空窗口，但首条消息后共享后台的 hook 可能没有终端标识；同目录多个会话时无法可靠合并。除非可证明映射，否则不能声称支持准确跳转与去重。
3. **只读发现真实会话并验证终端映射**：先验证 Codex 本地可观测信息能否在默认共享后台及 `--no-daemon` 模式中，把 TUI、真实 ID 和终端可靠关联；成立时由 SessionStore 合并到现有数据流。验证不成立的情况不能猜测或误跳，应保留现有 hook 行为并说明能力边界。

推荐先验证方案 3。只有在真实身份映射可证实时，才采用真实 ID 作为稳定键；否则需另行确定临时条目的交互与歧义处理，不能把推测结果伪装成真实会话。

## 已确认的降级方案

把确定存在的 Codex 终端显示为「待关联」临时条目，并显示入职工牌；进程信息不能证明用户尚未输入，因此不标成「未开始」。临时条目以 PID 和进程启动身份区分，不伪造真实会话 ID，也不提供按会话 ID 恢复的操作。只有能唯一证明对应关系时才与 hook 会话合并；同目录多窗口等无法证明的情况，明确展示未关联状态，不猜测跳转或合并。若临时条目消失，只有确认对应进程退出才显示离职，瞬时读失败不当退出。该方案能改善空窗口可见性，但不能保证所有共享后台会话在首条输入后自动合并。

## 验证与通过标准

1. 使用独立临时会话目录和隔离测试环境分别启动默认共享后台及 `--no-daemon` TUI，不发送消息；记录 TUI PID、tty、真实 ID 的可用来源及生命周期，不输出会话内容或凭据。
2. 同目录同时启动两个空 TUI、先后输入和关闭，证明真实 ID 与 tty 的关联是唯一且可重复的；测试恢复旧会话、后台重启、PID 复用和不可读数据。
3. 若映射成立，补充 SessionStore 的发现、去重与关闭回归：空会话一次入职；首条输入后同一条记录更新；退出一次离职；临时读失败不误关；不触碰用户真实会话数据。
4. 运行 `swift test` 和 `./scripts/install.sh --build`，并在真实交互式 TUI 中验证空开、输入、退出和两个同目录窗口。验证失败时不以单窗口通过代替多窗口通过。

## 已知风险与停止条件

本地 Codex 的状态库、锁文件与进程关系不是 Tally 的既有接口，版本更新可能改变；读取失败应保留既有 hook 结果。若无法验证默认共享后台的唯一映射，停止实现准确跳转和自动合并，不以目录或时间先后猜测。二十分钟没有新证据或同一路径失败两次时汇报；不改写用户数据。

## 影响与回退

受影响的是本地会话发现、AI 列表、角色名册和工牌；不改变 hook 的外部输入契约。功能实现后应能通过移除新增发现路径恢复现有 hook 行为，已有未提交改动须保留。
